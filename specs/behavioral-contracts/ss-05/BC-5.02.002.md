# Behavioral Contract BC-5.02.002: json.dumps length oracle (63 cases)

## Description

The acceptance oracle for `pyfmt.DumpsLen` at the tool_use site: for each of 63 transcript `input` sources, Go must
compute `len(json.dumps(json.loads(src) or ""))` (SL:1147) exactly as CPython 3.11 does. The table pins integer
precision, float repr, string escaping, duplicate keys and key order in one place. It is committed as a
CPython-generated table (`internal/pyfmt/testdata/`), regenerated by a committed generator under the pinned oracle
(OD-104).

## Preconditions

1. `src` is the raw JSON text of a tool_use `input` value as it appears in a transcript line (UTF-8 bytes).
2. Go evaluates `DumpsLen(OrEmpty(Decode(src, ModeBytes, depthBudget)))`, where `OrEmpty(v)` = `v` if truthy
   else the string `""`; `depthBudget` is the call-site recursion budget (ADV-P2-D08; BC-5.02.003 PC-7).

## Postconditions

1. For every row below the Go result equals the `len` column; any mismatch fails the test.
2. The committed table is generated wholly by script from the pinned oracle (OD-142): every
   row's literal source bytes are constructed by the generator (the worded rows 40-53
   describe constructions by code point, not hand-recorded dumps), and the generator re-
   derives every `len`. No literal in the table is hand-recorded. The generator (recorded
   below, committed at `internal/pyfmt/testdata/gen/dumps_len_oracle.py`) is the single
   source of the table; CI fails if the committed table differs from a fresh generation.

## Invariants

1. The table is generated, never hand-edited: the generator script lives in `internal/pyfmt/testdata/gen/` and runs
   under the explicit CPython 3.11.x interpreter (OD-104, OD-108); CI fails if the committed table differs from a
   fresh generation.
2. Decoding numbers to float64 breaks rows 14-16, 24 and 61; any such regression fails this table.
